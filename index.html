我是承育，有電商營運與後勤背景，現在是金車電商部的自動化工程師，這個職位是公司為了自動化新設的。

我的工作從坐到需求人旁邊開始：看他怎麼做、哪裡會出錯、出錯了誰會痛。接著把流程拆成步驟、寫成規格，用 AI 協作產出程式，經過兩輪審查、在測試環境驗證後才上線。

比起「省了幾小時」，我更在意的是：自動化上線之後，出事時有沒有人知道、能不能退回、後面接手的人看不看得懂當初為什麼這樣做。

A

需求 → 規格

訪談第一線、拆步驟、畫流程圖，把「大家都這樣做」變成寫得下來、可以驗收的規格。

B

落地與維運

用 Python、GAS、VBA 做自動化，串接公司系統與電商平台，部署在內網伺服器（VM）常駐，上線後持續維運。

C

風險控管

測試帳號優先、上線前新舊比對、保留退回人工的開關；每個決定都寫下前提與代價。

WHY

自動化不該只活在某個人的電腦裡

很多團隊的自動化，停在「某個人電腦上的一支腳本」。那個人一請假或離職，就沒人會修。我想做的是讓自動化變成團隊接得住的日常工具：大家看得到它在跑、出事會被通知、壞了有人知道怎麼退回。

CASE 01

自建 API 上線：補上最後一哩路，打通「全系統直連」

金車・2026.08 上線運作中
問題
公司系統沒有讓程式寫入的入口，自動化做到最後一步，還是得靠人上傳。
做法
自建 REST API，放在內網伺服器（VM）24 小時常駐、用金鑰驗證，讓腳本直接寫入公司系統。
取捨
  • 放內網、不放雲端。免去 VPN 申請與資安審查。代價：外部連不進來，伺服器要自己顧。
  • 一支 API 撐多條流程。所以加上自動重啟與每 10 分鐘巡檢。代價：多一套常駐服務要照顧。
成效
官網訂單、出貨轉業績兩條流程已由它接手、人不必介入；上線前壓測 330 筆零破損。
自建 REST APIFastAPISQL Server金鑰驗證內網常駐

CASE 02

官網訂單全自動匯入

金車・2026.08 上線運作中
問題
每月約 40 批、每批 20 分鐘人工處理；而且公司系統不讓我方刪除，匯錯了收不回來。
做法
抓單 → 篩選 → 匯入 → 對帳 → 通知，全程排程自動跑；匯入交給自建 API（見 CASE 01）。
取捨
  • 先比對、再切換。新舊並行，4,095 格零差異才切換。代價：上線晚一輪。
  • 永遠留退路。改一行設定就能退回人工。代價：人工做法要一直有人會。
成效
2026.08.05 起人工匯入停用，每批自動對帳。
Python排程自動化自動對帳新舊並行比對

DEMO上線前的「影子比對」：同一批訂單，舊路（人工）和新路（API）各匯一次，逐格對照，全部一致才開放切換。

舊路：人工匯入基準
新路：API 匯入待驗證
已比對 0 / 20 格・差異 0

按「開始比對」；也可以先試「模擬：新版有 bug」，看比對抓到錯誤時會怎樣。

範例資料。實際上線前比對的是 195 張單、4,095 格，全部一致才切換。

STEP 04

我的工作方式

HOW I WORK

程式大量由 AI 產出；規格、邊界、出事怎麼處理，由我決定。

因為那需要知道這些流程在業務上會怎麼壞、壞了誰會痛，這些 AI 不會知道。

我負責AI 負責一起做
  1. 01
    需求訪談

    看第一線怎麼做、哪裡會出錯

  2. 02
    拆步驟、畫流程

    每一步寫清楚輸入與輸出

  3. 03
    定規格與邊界

    什麼情況要停、通知誰、能不能退回

  4. 04
    產出程式

    依規格產出，不靠我手寫

  5. 05
    兩輪審查

    獨立審查員挑錯，有爭議由我決定

  6. 06
    測試驗證

    AI 先在測試環境跑，我用真實資料驗收

  7. 07
    上線、留紀錄

    我部署上線，AI 寫紀錄、我確認內容

PRINCIPLE 01

前提由我負責

前提錯了，後面推得再漂亮都是錯的。

AI 算出「週五失敗要等 72 小時才會被處理」。我指出營業所週末本來就不出貨，實際缺口是 0。
PRINCIPLE 02

每個決定都寫下代價

不只寫「為什麼這樣做」，也寫「這樣做會換來什麼問題」。

控制台累積 57 條決策紀錄，每條都有前提與已知代價；推翻舊決定時，也留下推翻的原因。
PRINCIPLE 03

先求不出事，再求快

自動化的價值，常常是「什麼都沒發生」。

測試帳號與測試庫優先；上線前新舊並行比對；每個自動化都保留退回人工的開關。
